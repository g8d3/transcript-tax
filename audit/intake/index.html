1. The three questions

  1. Volume. How many loops, how many turns per loop per day, and how many working days a year? (This is what turns a per-turn number into hours and dollars.)
  2. Cost per turn. Which model(s), which route or provider serves them, and what you pay per million input and output tokens; roughly how many input tokens a turn carries, and how much of that input repeats turn after turn (cached or not). The route matters as much as the model: on our own keys one model's input price runs 20.5x between routes and another's first token is 5.7x slower on the cheap route — the measurements are public.
  3. Process model. Does a turn start a process — a CLI or agent per turn — or does a warm service handle it? This decides whether the 929 ms of boot we measure per turn is in your bill at all. It is the one lever we have measured as real and removable, and it is worth 65 wall-hours a year at 10 loops × 100 turns/day.

2. What to attach

  • Preferred: the turn log your monitor already writes, <workspace>/.pi-web/tps-turns.jsonl. Those rows carry a timestamp, the model, token counts and segment durations — no prompt text, no tool output. One file is enough to start; you can check exactly what is in it by dropping it into the preview, which reads it in your browser.
  • Any other harness (Claude Code, Codex, a custom loop): a day of logs in whatever shape it already writes them. Writing the adapter is part of the audit — that is why the preview reads our format and the audit does not.
  • Never: API keys, wallet keys, funds, source code or production credentials. The work is read-only and we do not need write access to anything.
